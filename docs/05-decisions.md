## ADR-01. DOCX 판정을 ML에서 규칙 기반으로 전환

**맥락**: 기존 DOCX 모델(VotingClassifier 앙상블)은 테스트 정확도 1.00으로 기록돼 있었다. 학습 데이터 재검증 결과:

| 검증 항목 | 결과 |
|---|---|
| 악성 표본의 내용 피처 결측 | 940건 중 929건 (98.8%). `SimpleImputer(strategy="mean")`으로 대체된 상태로 학습 |
| 단일 피처 분리도 (depth-1 결정 트리) | `creation_time` 0.964, `modification_time` 0.964, `file_size` 0.931 |
| 추론 전처리 | 입력 1건으로 `StandardScaler`를 `fit_transform` → 출력이 항상 0 벡터 |

결측 대체값 패턴과 수집 시각이 라벨을 결정하고 있어, 모델은 문서 특성을 학습하지 않았다.

**결정**: DOCX는 공격 기법 단위 정적 규칙으로 판정한다. 규칙 명세는 [03-detection-engines.md](03-detection-engines.md#2-docx-규칙-엔진).

**대안**:
- 원본 DOCX 표본 재수집 후 재학습: 원본 파일이 저장소에 없어 현 시점에서 불가.
- 누수 피처 제거 후 재학습: 악성 표본 중 내용 피처가 있는 것이 11건뿐이라 학습 불가.

**결과**: 탐지 근거를 파트 경로와 대상 URL 수준으로 제시할 수 있다. 미지의 기법은 규칙 추가 전까지 탐지하지 못한다. 원본 데이터는 `training/data/legacy_docx/`에 보존한다.

## ADR-02. PDF 피처 추출기를 학습·추론이 공유

**맥락**: 학습 노트북은 `StandardScaler → SMOTE → VarianceThreshold → SelectKBest(k=10)`을 거친 입력으로 모델을 학습했으나 모델 객체만 저장했다. 추론 스크립트는 다른 10개 피처를 스케일링 없이 입력했다.

**결정**:
- `awake/pdf_features.py`를 단일 피처 정의로 두고 학습·추론이 모두 import 한다.
- 전처리와 분류기를 `imblearn.pipeline.Pipeline` 하나로 직렬화한다.
- 피처 이름 목록을 모델과 함께 저장하고, 로드 시 현재 정의와 다르면 `RuntimeError`로 중단한다.

**결과**: 학습·추론 불일치가 실행 시점에 차단되며, `test_saved_model_matches_extractor`가 이를 회귀 테스트한다.

## ADR-03. 감시(C)와 분석(Python) 프로세스 분리

**맥락**: 이벤트 감지는 상주성과 낮은 자원 사용이, 분석은 PDF·ML·LLM 라이브러리 생태계가 중요하다.

**결정**: C 감시기가 메일마다 Python 파이프라인을 별도 프로세스로 실행한다. 인터페이스는 argv의 메일 경로 1개와 종료 코드로 한정한다.

**대안**: Python 단일 상주 프로세스(watchdog + 분석). 프로세스 생성 비용이 없으나, 분석 중 예외·메모리 누수가 감시 기능에 전파된다.

**결과**: 분석 실패가 감시기에 격리되고, 실패 메일은 원위치에 남는다. 대신 메일마다 인터프리터 기동 비용이 발생하며, PDF 첨부가 있으면 모델 로드(약 1.1초)가 매번 반복된다. 측정값은 [06-test-report.md](06-test-report.md#5-처리-성능). 고처리량 환경에서는 모델을 상주 로드하는 분석 데몬 구조가 필요하며 [07-audit.md](07-audit.md#6-잔여-리스크-및-향후-과제)에 과제로 등록했다.

## ADR-04. 셸을 경유하지 않는 프로세스 실행

**맥락**: 기존 감시기는 `snprintf(command, ..., "python3 %s %s/%s", ...)` 후 `system(command)`를 호출했다. Maildir 파일명은 MTA가 생성하지만, 감시 폴더에 쓰기 권한이 있는 다른 경로로 파일이 유입되면 파일명이 셸 구문으로 해석된다.

**결정**: `execvp(py, {py, "-m", "awake.pipeline", "--deliver", path, NULL})`. 추가로 `.` 시작 이름, `/` 포함 이름, `lstat` 기준 비정규 파일을 제외한다.

## ADR-05. 분석 대상을 이벤트 경로로 명시 전달

**맥락**: 기존 LLM 분석기는 수신 폴더에서 `mtime`이 최대인 파일을 선택했고, 후처리기는 그 결과를 다른 JSON 파일을 통해 읽었다. 짧은 간격으로 메일 2통이 도착하면 판정 대상과 이동 대상이 달라질 수 있다.

**결정**: 이벤트로 받은 경로를 파이프라인에 직접 전달하고, 분석부터 이동까지 단일 프로세스에서 수행한다. 중간 JSON 파일 경유를 제거한다.

## ADR-06. 엔진 판정의 논리합 정책

**결정**: $\exists v_i = 1 \Rightarrow$ 악성. `None`은 집계에서 제외한다.

**근거**: 메일 보안에서 미탐(악성 전달)의 피해가 오탐(정상 격리)보다 크고, 격리는 복구 가능한 조치다.

**트레이드오프**: 엔진별 오탐이 누적된다. 현재 PDF 모델의 균형 정확도(0.745)를 고려하면 정상 PDF 첨부 메일의 오격리가 발생할 수 있으며, 운영 시 `PDF_THRESHOLD` 조정 또는 가중 투표 도입이 필요하다.

## ADR-07. LLM 판정의 최종 행 제한

**맥락**: 메일 본문은 공격자가 통제한다. 응답 전체에서 판정 문자열을 검색하면, 본문에 삽입된 문구를 모델이 인용하는 것만으로 판정이 바뀐다.

**결정**:
- 메일 내용을 호출마다 생성하는 64비트 난수 구분자로 감싼다.
- 시스템 프롬프트에서 구분자 내부의 지시를 무시하도록 명시한다.
- 공백이 아닌 마지막 행이 `^\s*VERDICT:\s*(MALICIOUS|BENIGN)\s*$`과 일치할 때만 판정으로 인정한다.

**한계**: 프롬프트 인젝션을 완전히 차단하지 못한다. LLM은 보조 엔진으로 두고, 정적 분석 결과를 무효화하는 권한을 갖지 않는다(논리합 정책상 LLM의 `BENIGN`은 다른 엔진의 악성 판정을 뒤집지 못함).
