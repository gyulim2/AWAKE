# 06. 회고

## 1. 프로젝트 개요와 역할

| 항목 | 내용 |
|---|---|
| 형태 | KISIA 교육과정 4인 팀 프로젝트 |
| 시기 | 2024년 (원본 파일 날짜 기준 가을) / 2026년 10월 개인 저장소로 옮겨 전면 정리 |
| 역할 | 팀장. 시스템 구조(Maildir 연동, 감시기 → 분석 파이프라인 흐름)를 설계하고 핵심 코드 대부분을 작성. 팀원과 작업을 나눠 주고받으며 진행해 세부 분담은 명확히 구분되지 않음 |

원래 팀 저장소의 커밋 이력은 옮겨 오지 않았다. 이 저장소의 이력은 2026년 10월부터 시작한다.

## 2. 2026년 정리에서 발견한 문제

2026년에 코드를 다시 읽고 실행해 보니, 저장소에 남아 있던 코드 기준으로 여러 군데가 끊겨 있었다. (당시 시연 환경에 저장소와 다른 파일이 있었는지는 남은 기록이 없어 알 수 없다.) 원인 칸은 코드와 데이터에서 확인되는 사실이고, "추정"으로 표시한 것은 확인할 수 없는 추정이다.

| 문제 | 영향 | 원인 |
|---|---|---|
| 감시기가 존재하지 않는 `python_script.py`를 호출 | 새 메일이 와도 분석이 실행되지 않음 | 호출 대상 파일이 저장소에 없음 (이름을 바꾸며 감시기를 갱신하지 않은 것으로 추정) |
| DOCX 정확도 100% | 실제로는 의미 없는 모델 | 악성 929/940개 파싱 실패 + 결측 평균 대체, 파일 생성 시각 누수 |
| DOCX 추론 입력이 항상 0 | 모든 DOCX에 같은 판정 | 샘플 1개로 스케일러를 새로 학습 |
| PDF 학습/추론 피처 불일치 | 모델에 엉뚱한 값이 들어감 | 학습(노트북)과 추론(스크립트) 코드가 따로 있었음 |
| PDF 평가에 SMOTE 누수 | 성능 수치를 신뢰하기 어려움 | 데이터 분할 전에 오버샘플링 |
| `system()`에 파일명 연결 | 셸 명령 주입 가능 | 문자열을 이어 붙여 `system()`에 전달 |
| "가장 최근 파일"을 분석 | 동시 수신 시 다른 메일을 판정·이동 | 감시기와 분석기 사이에 메일 경로를 넘기지 않음 |
| 첫 번째 첨부만 분석, 첨부가 있으면 링크 무시 | 탐지 누락 | |
| GUI 시안 4개, 바이너리·zip 커밋 | 어떤 파일이 실제 버전인지 알 수 없음 | 같은 기능의 파일이 이름만 바꿔 여러 개 존재 (파일을 복사해 가며 작업한 것으로 추정) |

공통점은 **문제가 모두 부분과 부분이 만나는 경계에 있었다**는 것이다. 학습 노트북 안에서는 정확도가 잘 나오고 각 스크립트도 단독으로는 실행되지만, 감시기 → 분석 → 격리로 이어 붙인 전체 흐름과 학습 → 추론 연결을 자동으로 검증하는 테스트가 저장소에 없었다.

## 3. 어떻게 고쳤나

- 문제마다 원인을 데이터와 코드로 먼저 확인했다. 예를 들어 DOCX는 "정확도가 너무 높다"는 의심에서 출발해 피처별로 한 번만 나눠 보는 분류(depth-1 tree)를 돌렸고, 생성 시각 하나로 96.4%가 갈리는 것을 확인한 뒤 데이터를 버리기로 결정했다.
- 학습과 추론이 같은 코드를 쓰게 구조를 바꾸고(ADR-02), 결함 있는 데이터로 숫자를 맞추는 대신 근거를 설명할 수 있는 규칙으로 바꿨다(ADR-01).
- 감시기부터 격리까지 이어지는 흐름을 테스트로 묶고, CI에서 매번 확인하게 했다.
- 정리 작업은 AI 코딩 도구(Claude)와 함께 진행했다. 문제 발견, 원인 검증, 수정, 테스트 작성 과정을 함께 했고, 커밋에 공동 작성자로 기록돼 있다.

## 4. 배운 점

1. **좋은 성능 수치는 먼저 의심한다.** 정확도 100%는 축하할 일이 아니라 누수를 찾아야 한다는 신호였다.
2. **학습 코드와 서비스 코드는 하나여야 한다.** 피처 추출이 두 군데에 있으면 언젠가 반드시 어긋난다.
3. **연결 부분이 가장 잘 깨진다.** 모듈마다 잘 돌아도 경계(감시기 ↔ 분석기, 학습 ↔ 추론)에서 문제가 생겼다. 전체 흐름 테스트가 필요하다.
4. **보안 도구 자체도 공격 대상이다.** 메일 분석기는 공격자가 만든 파일명과 내용을 다루므로, 셸 실행·프롬프트·압축 해제 모두 입력을 의심하는 방식으로 짜야 한다.

## 5. 남은 한계와 개선 계획

| 한계 | 개선 방향 |
|---|---|
| 정상 PDF 샘플이 102개뿐이고 출처 차이를 학습했을 가능성 | 정상 업무 문서 PDF를 더 모아 재학습, 출처가 같은 데이터로 검증 |
| DOCX 규칙은 알려진 기법만 탐지 | 엑셀(XLSX/XLSM)·RTF로 규칙 확장, oletools 연동 검토 |
| LLM 실제 성능 미측정 | 공개 피싱 메일 데이터셋으로 판정 정확도·비용 측정 |
| 링크는 문맥으로만 판단 | URL 평판 조회(예: 위협 인텔리전스 피드) 연동 |
| 메일마다 Python 프로세스를 새로 실행 | 메일량이 많아지면 분석 데몬 + 작업 큐 구조로 전환 |
| 탐지 결과가 JSON 파일로만 남음 | SIEM(예: Elastic)으로 전송해 관제 대시보드에서 조회 |
